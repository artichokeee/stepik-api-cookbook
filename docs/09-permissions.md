# 09. Права, команда, рецензирование

## Роли – это группы

Роль в курсе – членство в группе. id групп лежат в полях курса:

| Поле курса | Роль |
|---|---|
| `admins_group` | администраторы |
| `teachers_group` | преподаватели |
| `assistants_group` | ассистенты |
| `moderators_group` | модераторы |
| `testers_group` | тестировщики |
| `learners_group` | ученики |

**Никогда не листайте участников `learners_group`.** Это все ученики курса – тысячи страниц, и это чужие данные, которые скрипту автора не нужны.

### Можно ли управлять группой

`GET /api/groups?ids[]=...` → `{category, members_count, actions: {manage_members: {enabled}}}`.

**Ожидание:** право управлять ролью зависит от вашей роли, его можно вывести заранее.
**На деле:** набор доступных ролей зависит и от курса: на одних курсах управлять можно только администраторами и модераторами.
**Что делать:** смотрите `actions.manage_members.enabled` у каждой группы – это единственный честный признак. Не зашивайте правило в код.

### Участники

| Что | Запрос |
|---|---|
| список | `GET /api/members?group=<groupId>` |
| добавить | `POST /api/members` с `{"member": {"group": ..., "user": ...}}` или `{"group": ..., "email": ...}` |
| убрать | `DELETE /api/members/<id>` |

### Приглашения

- Создать: `POST /api/invitations` с `{"invitation": {"group": ..., "limit": 1}}`. `limit: 1` – одноразовое, `limit: null` – многоразовое.
- `url` в ответе – **относительный** путь; полный адрес собирайте сами, приставив `https://stepik.org`.
- Список: `GET /api/invitations?group=<groupId>`. Фильтр `?course=` возвращает пустой список.

## Баны в своем курсе

- Список: `GET /api/bans?course=<id>` – этот фильтр работает.
- Создать: `POST /api/bans` с `{"ban": {"course": ..., "banned_user": ..., "comment": "...", "expire_date": null}}`.
- `comment` обязателен, до 1000 символов. `expire_date: null` – бессрочно.
- Правка – `PUT /api/bans/<id>` с теми же полями, снятие – `DELETE /api/bans/<id>`.

## Рецензирование

Документации нет; ниже – порядок, который работает.

### Задание на рецензирование

- `instruction` привязывается только к шагу с заданием. На текстовом шаге – ошибка "Not a quiz"; `free-answer` подходит.
- `strategy_type` записывается **числом** (1 – взаимная проверка, 2 – проверка преподавателем), а читается **строкой**.
- Шаги курса с рецензированием находите по полю `instruction` самих шагов (`GET /api/steps?ids[]=...` пачками по 30). `instructions?course=` возвращает пустой список, а `instructions?step=` принимает только один шаг.
- Критерии: `GET /api/rubrics?instruction=<id>`, создание – `POST /api/rubrics` с `{instruction, text, cost, position}`.

### Сессии

`GET /api/review-sessions?instruction=<id>` – и только так.

**Ожидание:** `review-sessions?course=<id>` вернет сессии курса.
**На деле:** фильтр игнорируется, приходят сессии **текущего пользователя** по всем курсам. Счетчик на таком запросе однажды посчитал одну тестовую сессию для каждого курса.
**Что делать:** только `?instruction=`.

### Отправка рецензии

**Ожидание:** рецензия с баллами – один `POST /api/reviews` с вложенными оценками.
**На деле:** вложенные баллы не принимаются ("Expected pk value, received dict"), а `POST /api/rubric-scores` запрещен.
**Что делать:** четыре шага:

1. `POST /api/reviews` с `{"review": {"session": <ваша сессия проверяющего>, "submission": <решение>, "text": "...", "rubric_scores": []}}`. `session` – **ваша** сессия проверяющего по этому заданию (найти – `review-sessions?instruction=<id>&user=<ваш id>`, нет – создать `POST /api/review-sessions` с `{"reviewSession": {"instruction": <id>}}`), а не сессия автора решения. Stepik сам заведет по объекту оценки на каждый критерий и вернет их id в `rubric_scores`.
2. Баллы – `PUT /api/rubric-scores/<id>` с `{"rubricScore": {"id": <id>, "score": <балл>}}` для каждого.
3. Завершение – `PUT /api/reviews/<id>`, снова с **пустым** `rubric_scores`. Настоящие id здесь отклоняются как "object does not exist".
4. После завершения у рецензии заполнено `when_finished`, решение оценено.

### "Ждет проверки"

**Ожидание:** решение ждет проверки, пока у сессии `is_finished: false`.
**На деле:** после рецензии решение уже оценено, а `is_finished` остается `false`. Фильтр `?is_finished=` Stepik игнорирует.
**Что делать:** решение ждет проверки, когда `taken_reviews.length < min_reviews`.
