# 03. Чтение

## Формат ответа

Ответ – всегда объект, где нужные данные лежат списком под ключом во множественном числе, совпадающим с именем ресурса:

```json
{ "meta": { "page": 1, "has_next": true, "has_previous": false }, "lessons": [ { "id": 1, "title": "..." } ] }
```

- Даже `GET /api/lessons/<id>` возвращает список из одного элемента: `lessons[0]`. Пустой список вместо объекта – значит, объекта нет или он вам недоступен.
- Ключ повторяет имя ресурса буквально, с дефисом: `step-sources`, `step-sources/<id>`.
- Кроме основного ключа в ответе бывают соседние: `GET /api/stepics/1` отдает и `stepics`, и `users`.

## Пагинация

Списки отдаются страницами. Признак продолжения – `meta.has_next`, следующая страница – параметр `page` (с 1):

```python
items, page = [], 1
while page <= 50:                      # верхняя граница на случай ошибки
    d = get("/courses", {"teacher": me, "page": page})
    items += d["courses"]
    if not d["meta"]["has_next"]:
        break
    page += 1
```

Ставьте верхнюю границу числа страниц. Некоторые списки огромны (см. `learners_group` в [09-permissions.md](09-permissions.md)), и цикл без границы будет листать их часами.

## Чтение по id

Несколько объектов одного типа – одним запросом через `ids[]`:

```
GET /api/lessons?ids[]=101&ids[]=102&ids[]=103
```

- Держите пачку в пределах 30 id: так читаются и уроки, и шаги, и привязки.
- Объекты, к которым у вас нет доступа, Stepik молча не вернет. Сверяйте число полученных объектов с числом запрошенных.
- В curl добавляйте `-g`, иначе он попытается разобрать `[]` сам. `requests` с `params={"ids[]": [...]}` кодирует скобки, и Stepik это понимает.

## Фильтры, которые работают и которые врут

Неизвестный или неподдерживаемый фильтр Stepik не отклоняет, а молча игнорирует или отвечает пустым списком. Пустой ответ – не доказательство, что объектов нет. Проверяйте новый фильтр на объекте, о котором точно знаете, что он есть.

| Запрос | Ожидание | На деле | Что делать |
|---|---|---|---|
| `sections?course=<id>` | модули курса | пустой список | `course.sections` → `sections?ids[]` |
| `courses?teacher=<userId>` | все курсы преподавателя | курс, где вы соавтор, может не прийти | известные курсы дочитывайте по `courses?ids[]` |
| `units?lesson=<id>` | привязка урока | работает | – |
| `comments?course=<id>&parent=null` | корневые комментарии курса | работает, `target` в ответе – id шага | ответы – `comments?parent=<id>` |
| `invitations?course=<id>` | приглашения в команду | пустой список | `invitations?group=<groupId>` |
| `instructions?course=<id>` | задания на рецензирование | пустой список | поле `instruction` у шагов: `steps?ids[]` |
| `review-sessions?course=<id>` | сессии рецензирования курса | молча отдает сессии **текущего пользователя**, курс игнорирует | только `review-sessions?instruction=<id>` |
| `review-sessions?is_finished=` | только завершенные | фильтр игнорируется | см. [09-permissions.md](09-permissions.md#рецензирование) |
| `announcements?user=<ownerId>` | все рассылки автора, включая триггеры курсов | триггеры курсов не приходят | `announcements?course=<id>` |
| `bans?course=<id>` | баны курса | работает | – |
| `notifications?type=comments` | уведомления о комментариях | работает | без `type` уведомления разных видов идут вперемешку |

Самый опасный случай – `review-sessions?course=`: ответ выглядит правдоподобно, и счетчик, построенный на нем, считает одну и ту же вашу сессию для каждого курса.

## Темп

API стоит за защитой от DDoS (QRATOR). Читайте последовательно или небольшим числом параллельных запросов, с паузой около 350 мс между запросами. Подробно – в [08-errors-and-limits.md](08-errors-and-limits.md).

## Состояние шага

Готов ли шаг с заданием к решению, видно только в `/api/steps`: поля `status` (`ready` или `error`) и `reason_of_failure`. В `/api/step-sources` этих полей нет. Подробно – в [04-writing.md](04-writing.md#201-created-не-значит-что-шаг-работает).
