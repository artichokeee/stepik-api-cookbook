# 01. Авторизация

Stepik – обычный OAuth2-сервер. Способов получить токен два, и у одного приложения он ровно один.

| Задача | Способ | Тип приложения |
|---|---|---|
| Скрипты для своего аккаунта | `client_credentials` | Confidential, grant type "Client credentials" |
| Свой сервис, куда другие авторы входят через Stepik | `authorization_code` | отдельное приложение с grant type "Authorization code" |

## Адреса

| Что | Адрес |
|---|---|
| Список приложений | https://stepik.org/oauth2/applications/ |
| Регистрация приложения | https://stepik.org/oauth2/applications/register/ |
| Подтверждение доступа | `https://stepik.org/oauth2/authorize/` |
| Выдача токена | `https://stepik.org/oauth2/token/` |
| API | `https://stepik.org/api/...` |

## client_credentials: скрипты для своего аккаунта

```bash
curl -s -X POST https://stepik.org/oauth2/token/ \
  -u "$STEPIK_CLIENT_ID:$STEPIK_CLIENT_SECRET" \
  -d grant_type=client_credentials
```

- Client id и secret идут в заголовке `Authorization: Basic …` (у curl – ключ `-u`), тело – форма `application/x-www-form-urlencoded`.
- В ответе `access_token` и `expires_in` в секундах. Обычно это 36000, то есть 10 часов.
- Дальше каждый запрос к API несет заголовок `Authorization: Bearer <access_token>`.
- Новый токен берите заранее, примерно за минуту до истечения, а не после первого 401.
- Если несколько потоков одновременно увидели, что токена нет, пусть за ним сходит один, а остальные дождутся его ответа.

Пара Client id + Client secret дает полный доступ к аккаунту и не истекает. Держите ее в переменных окружения, не в репозитории. Отдать ее чужому сервису – значит отдать аккаунт.

### Кто я

```bash
curl -s -H "Authorization: Bearer $TOKEN" https://stepik.org/api/stepics/1
```

`GET /api/stepics/1` возвращает текущего пользователя по токену: число лежит в `stepics[0].user`, а профиль – в `users[0]` (`users[0].id` – то же число). Свой числовой id не нужно искать в адресной строке профиля – этот запрос отвечает точно.

## authorization_code: вход через Stepik для своего сервиса

Нужен, когда сервисом пользуются другие авторы. Человек подтверждает доступ на самом Stepik и ничего не вводит у вас; отозвать доступ он может в своем профиле Stepik, в списке приложений.

**Ожидание:** одно приложение можно настроить и на `client_credentials`, и на вход пользователей.
**На деле:** тип авторизации у приложения один. Второй режим отвечает `unauthorized_client`.
**Что делать:** заведите для входа пользователей отдельное приложение со своими client id и secret.

### Шаги

1. Отправьте человека на подтверждение:

```
https://stepik.org/oauth2/authorize/?response_type=code&client_id=CLIENT_ID&redirect_uri=REDIRECT_URI&state=STATE
```

   `redirect_uri` должен быть зарегистрирован в приложении, иначе Stepik его не примет. Если у сервиса несколько адресов (рабочий и тестовый), зарегистрируйте все. `state` – случайная строка, которую вы сверяете при возврате.

2. Обменяйте код на токены:

```bash
curl -s -X POST https://stepik.org/oauth2/token/ \
  -u "$CLIENT_ID:$CLIENT_SECRET" \
  -d grant_type=authorization_code -d code="$CODE" -d redirect_uri="$REDIRECT_URI"
```

   В ответе `access_token`, `refresh_token`, `expires_in`. Если `refresh_token` не пришел, не продолжайте: без него доступ молча отвалится через 10 часов.

3. Обновляйте доступ по refresh-токену:

```bash
curl -s -X POST https://stepik.org/oauth2/token/ \
  -u "$CLIENT_ID:$CLIENT_SECRET" \
  -d grant_type=refresh_token -d refresh_token="$REFRESH"
```

### Refresh-токен одноразовый

**Ожидание:** refresh-токен можно использовать много раз.
**На деле:** при обновлении Stepik выдает новый refresh-токен и гасит прежний.
**Что делать:** сохраняйте новый refresh-токен сразу, дождавшись записи, и только потом работайте дальше. Не сохранили – при следующем обновлении человек окажется разлогинен.

**Ожидание:** отказ при обновлении значит, что человек отозвал доступ.
**На деле:** то же самое бывает, когда два процесса (например, старая и новая версия сервиса во время выкладки) обновляют один и тот же токен: кто успел первым, погасил токен второго.
**Что делать:** при 400/401 на обновлении перечитайте сохраненный refresh-токен; если он новее вашего, повторите обновление с ним один раз. Только после этого считайте доступ отозванным.

Храните только refresh-токен (зашифрованным), access держите в памяти процесса. Так перезапуск не разлогинивает людей, а в базе нет ключа, которым можно прямо сейчас ходить в Stepik.

## Ошибки выдачи токена

| Ответ | Что значит |
|---|---|
| `invalid_grant` | код подтверждения не принят или refresh-токен уже погашен – нужно подключиться заново |
| `invalid_client`, `unauthorized_client` | неверные client id/secret или тип приложения не тот |
| 429, 5xx | временный сбой; повторяйте так же, как обычные запросы ([08-errors-and-limits.md](08-errors-and-limits.md)) |

Ставьте таймаут и на запрос токена (20 секунд хватает): без него зависший вызов подвешивает все, что ждет токен.

## Только с сервера

**Ожидание:** API можно вызвать из браузера.
**На деле:** CORS у API нет, браузер такой запрос не выполнит.
**Что делать:** ходите в API из скрипта или со своего сервера; секрет приложения в браузер не попадает никогда.
